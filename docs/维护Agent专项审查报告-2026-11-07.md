## 第二章 细化展开

### 2.1 [P1] 任务结束后页面永久"忙碌"卡死(running 标记前端从不维护)

**现象**:会话列表里的 `running` 标记只在页面加载时从服务端取值一次,此后前端任何路径都不再更新它。任务执行中刷新页面 → 自动选中并订阅该会话 → 任务跑完后流式收尾只把 `isStreaming` 置回 false,但 `currentSession.running` 仍为 true,而页面用 `busy = isStreaming || currentSession?.running` 判定占用(`AgentChat.vue:216`)→ `busy` 恒为 true。点"停止"也无效(任务已结束,后端返回 `stopped:false`,前端不清 running)。唯一恢复方式是刷新整页让列表重新拉取。

**位置**:`frontend/src/stores/agent.ts:153`(selectSession 依赖 running 决定是否订阅)、`:404-414`(followTask 收尾不清 running)、`:419-432`(stop 不清 running)、`:216-222`(send 成功后也不把本会话置 running);`frontend/src/views/Dashboard/AgentChat.vue:216、20、261、271`。

**影响**:设计明示的核心场景"刷新/关闭页面后重进续看"走完后页面不可再交互:输入框禁用、恒显示停止按钮、模型选择器禁用、删除/清空被拦截。同时存在孪生问题——在本会话发起任务后切走再切回,由于 send 从不置 `running=true`,`selectSession` 不会自动续订,页面看起来空闲,再发消息只会吃到 409,后台任务也不可发现。

**建议**:把 `running` 的本地生命周期管起来:followTask 收尾(且是当前订阅)与 stop 成功后置 `session.running=false`;send 成功后置 true;可顺带在会话列表项上加 running 视觉标记,收尾时静默刷新会话列表兜底。

### 2.2 [P2] 任务提交与事件订阅的竞态窗口,订阅端可能错过整场任务

**现象**:`POST /chat` 在创建后台任务后立即返回;但任务协程要先经历读会话、读用户、修复历史、落库用户消息、装配历史等多次异步数据库操作,**之后**才把事件总线注册进 `_BUS`。前端按协议"提交后立即订阅",若订阅落在该窗口内,`get_bus` 返回 None(或上一个已结束的旧总线),订阅端立即收到 `task_inactive` 收尾——而此时任务正在正常执行。

**位置**:`backend/app/services/agent/maintain_loop.py:115-120`(start_task 即返回)、`:346-364`(多次 await 后才 `_BUS[session_id] = bus`)、`:123-130`(bus 为 None/finished 直接 task_inactive);`backend/app/router/maintain_agent.py:228-235`;前端 `stores/agent.ts:216-222`(POST 返回后立即 followTask)。

**影响**:任务照常在后台跑,但页面收不到任何事件——流式输出、工具状态条、审批卡全部丢失。审批场景下表现为"发了指令却一直不弹卡",管理员只能刷新会话列表重新订阅才能续上。

**建议**:在 `start_task` 创建任务前同步预注册占位总线(或 stream 端点对"无总线但任务在跑"的情况短暂等待重查);并配合 2.18 在任务收尾时把 `_TASKS`/`_BUS` 条目一并清理,消除旧总线干扰。

### 2.3 [P2] 会话设置任务启动时快照,运行中切换模型/审批档位不生效

**现象**:任务启动时把 `model_name` 与 `approval_mode` 读出存进 `session_dict`,主循环内从不重读数据库。每轮开头的"模型纪元检查"拿冻结快照比较,结果永远相等 → 中途在库里改模型不会触发重新解析;工具执行器的审批阀门读的也是快照档位 → 任务全程锁定启动时档位。而设计文档 2.2/3.1 明确"prepare 读会话当前模型""前端选择器随时切换、下一轮生效",系统提示词还告诉模型"切换驱动模型下一轮生效"。

**位置**:`backend/app/services/agent/maintain_loop.py:357-361`(快照构造)、`:431`(纪元比较读快照)、`:447`;`backend/app/services/agent/registry.py:170`;`backend/app/router/maintain_agent.py:174-193`(PATCH 端点任务中可改库但任务不读)。

**影响**:长任务(40 轮、含 300 秒审批等待)期间管理员切换大脑模型或收紧/放宽审批档位均静默无效,易产生"我明明改成完全权限了为什么还弹卡"的困惑;模型窗口变化也不会触发重新压缩检查。前端帮助文案"随时换脑,下一轮生效"(AgentChat.vue:164)与任务中选择器禁用(:20)叠加,进一步放大承诺与实际的落差。

**建议**:每轮 prepare 前重查会话行(或至少在轮首刷新 `session_dict` 的 model_name/approval_mode),让既有纪元比较逻辑真正生效;短期可先修正前端帮助文案。

### 2.4 [P2] 沙箱实时输出绕过脱敏,原始输出进回放缓冲并被重放

**现象**:沙箱命令的 stdout/stderr 按 0.25s/2KB 批次**未经任何脱敏**即通过 emit 推送为 `sandbox_output` 事件,事件总线会把同一份原始字节写入回放缓冲(后续任何订阅者重连都会原样重放)。只有命令执行完毕后的最终结果才走注册表的 redact+8KB 截断管线。sandbox_service 模块注释声称"命令输出经现有 redact 管线回传",与实现不符。

**位置**:`backend/app/services/sandbox_service.py:328-338`(原始 chunk 直接 emit)、`:20-22` 附近模块注释;`backend/app/services/agent/maintain_loop.py:366-367`(emit→publish 写入缓冲)、`:70-75`;`backend/app/services/agent/registry.py:233`(仅最终结果脱敏)。

**影响**:密钥闭环"上下文/前端/消息表三处同源同过滤器"的前端通道被破口。沙箱在 MySQL 桥接模式下注入了数据库凭证,`printenv`、curl 回显等输出中的凭证会明文推送到前端并持久在回放缓冲中反复重放(缓冲上限 2000 条事件)。虽不进模型上下文与消息表,但违背自声明的安全不变量。

**建议**:emit 前对批次文本过一遍脱敏(纯文本可用密钥形态正则 + redact_text),保证回放缓冲只存脱敏后的事件;或在模块注释与设计文档中明确实时流不脱敏的边界。

### 2.5 [P2] 剥 tools 降级误判:单渠道一次 400/422 即永久降级整个任务

**现象**:发往上游的请求收到 400/422 且带 tools 时,一律按"模型不支持 function calling"处理:剥掉 tools 后在本渠道重试;若重试仍失败(真实原因可能是该渠道网关问题、上下文超窗、参数被拒等,与 tools 无关)则 break 到下一渠道——此时请求体已无 tools,后续渠道全部以无 tools 请求被探测。任一渠道最终成功,调用方即判定整个任务降级,后续轮次不再注入工具并向模型注入"当前模型不支持工具调用"的误导提示。

**位置**:`backend/app/services/agent/maintain_loop.py:637-643`(400/422 即 pop tools 并 continue)、`:644-649`(仍失败 break,body 已无 tools)、`:476-481`(tools_degraded 永久置位)。

**影响**:一次渠道级抖动或一次超窗 400(与 2.15 叠加)会让整个任务被判"模型不支持工具"并不可恢复地降级为纯对话,工具循环能力失效,还误导管理员去更换模型。降级判定也不随渠道切换复位。

**建议**:仅在"剥掉 tools 后同渠道立刻成功"时才确认降级;剥 tools 后仍失败应恢复 body 中的 tools 再试下一渠道;至少把降级与渠道维度解耦(换渠道后重新注入 tools 试探)。

### 2.6 [P2] dry-run 预览计入删除配额,真删有效上限退回 5 次

**现象**:会话配额按"工具名 + 非 isError 结果"计数,delete_channel / delete_model 的 `dry_run=true` 预览与 `dry_run=false` 真删各计 1 次——每次完整两段式删除消耗 2 个配额,单会话最多真删 5 次。设计文档 2.3 的端到端示例("批准后真删,会话配额计数 1/10")与附录 C 决策 #10"删除类从 5 放宽到 10(5 次撑不住批量清理)"在当前实现下名存实亡。

**位置**:`backend/app/services/agent/registry.py:218-219`(成功即计数,不区分 dry_run);`backend/app/services/agent/tools/channel_tools.py:304-325`、`model_tools.py:249-271`(dry_run=true 是正常成功返回);`backend/app/crud/agent.py:96-116`(计数口径);`docs/维护Agent设计文档.md:105`。

**影响**:护栏从紧方向偏移,无安全风险,但批量清理场景的实际可删次数约为设计意图的一半,且与文档示例直接矛盾。

**建议**:计数时对 `args.dry_run is True` 的调用豁免;若"dry-run 也算一次"是有意口径,则同步修订设计文档 2.3 示例与 4.3 说明。

### 2.7 [P2] 删除/清空运行中会话的防护不完整,产生孤儿消息与失控消耗

**现象**:三层防护都不完整:① 后端 delete/clear 端点不检查 `is_running` 也不调用 `stop_task`;② 前端只在"删除/清空**当前**会话"时检查 busy,右侧列表里另一条 running=true 的会话照常可删;③ 删除后服务端任务继续执行——LLM 轮次继续扣管理员余额、已批准的高危工具照常执行,且每轮 `insert_message` 向已不存在的 session_id 写消息(表无外键,插入成功)。消息 GC 的清理范围只来自现存会话行,这些孤儿消息永远清不到。

**位置**:`backend/app/router/maintain_agent.py:196-205`(delete)、`:208-213`(clear);`frontend/src/views/Dashboard/AgentChat.vue:259-267、270-282`(仅拦当前会话);`backend/app/crud/agent.py:196-232`(gc 范围);`backend/app/models/agent_message.py:27`(无外键注释)。前端 `removeSession` 也不先调 stop(对照 clearSessions 有调)。

**影响**:孤儿行永久累积、计数与保留策略失真;资金与工具消耗不受控;"删除即终止"的预期落空(AgentChat.vue:260 的注释自己点明了这个风险,但只防了一半)。

**建议**:delete/clear 端点先 `stop_task(session_id)` 再删,并顺带拒绝/停止 running 会话;`gc_sessions` 顺带清理 `session_id NOT IN (SELECT id FROM agent_session)` 的孤儿消息;前端删除前按目标会话的 running 标记拦截。

### 2.8 [P2] create_model 按次计费可不填单价,静默创建 0 元模型

**现象**:工具 handler 对四个价格字段只校验"非负",`is_request_mode=true` 而 `per_request_price` 缺省时不报错,service 层把 None 兜底为 0 落库——对外按次计费但单价 0 元,创建后即产生免费调用。

**位置**:`backend/app/services/agent/tools/model_tools.py:137-139`(仅非负校验)、schema 描述声称"按次模式必填";`backend/app/services/model_service.py:59-61`(None→0 兜底)。

**影响**:定价直接决定计费(该工具列为 L2 关键写的理由),这是一个静默的计费配置错误入口;审批卡预览会显示"按次计费 0 元/次",但依赖管理员肉眼发现。

**建议**:`is_request_mode=true` 时校验 `per_request_price` 必传且 > 0(管理页同类校验可对齐复用)。

### 2.9 [P2] 重进执行中任务时消息重复渲染(回放裁剪口径不一致)

**现象**:回放裁剪用 `messages.slice(0, baseMessages)`,而 `baseMessages` 是服务端按**数据库行数**(含 tool 行)统计的;前端 mapHistory 会把 tool 行并入前一个助手气泡,**UI 消息数 ≤ 行数**。当任务期之前的历史里已有工具行时,按行数裁剪截不掉任务期已落库的气泡,随后回放又把同样的增量重建一遍 → 同一轮正文与工具条出现两份,直至任务结束再次重进才自愈。

**位置**:`frontend/src/stores/agent.ts:287-289`(slice 裁剪)、`:45-74`(mapHistory 合并 tool 行);`backend/app/services/agent/maintain_loop.py:363`(`base_messages=len(history)` 按行数)。

**影响**:长任务中途重进是设计明示场景("重新进入会话自动回放+跟随"),该场景下几乎必现重复气泡。

**建议**:改用行 id 口径裁剪(replay_start 后按第 baseMessages 行的 id 截断 mapHistory 结果),或后端下发 UI 口径条数。

### 2.10 [P2] 会话切换竞态两处:提交在途劫持与连点覆盖

**现象**:① `send` 提交任务的 POST 在途期间用户切换到会话 B → POST 返回后 `followTask(旧会话)` 无条件执行,把订阅标记设回旧会话,回放与实时增量全部追加进 B 的消息列表(`alive()` 此时为真拦不住);首条消息的自动起标题也会打到 B 上。② `selectSession` 的消息请求无时序守卫,快速连点两个会话时,慢到的响应会把 `messages`/水位覆盖成非当前会话的内容,而高亮已是另一个。

**位置**:`frontend/src/stores/agent.ts:216-222、225-233`(劫持与标题)、`:128-157`(selectSession 无守卫)。

**影响**:A 的任务输出渲染进 B 的对话窗口并可能改写 B 的标题(数据污染);中栏显示错会话的消息,若 B 恰在跑任务再叠加 2.9 的回放裁剪,错乱放大。

**建议**:两个 await 之后校验 `currentSessionId` 未变再落地/续订,过期请求直接丢弃;send 的 followTask 前同样校验。

### 2.11 [P2] 审批卡交互缺陷:失败仍弹成功提示 + 无防连点

**现象**:① store 的 `approve` 在 catch 里弹"审批提交失败"后正常返回(不抛出、不返回结果),页面紧接着无条件弹绿色"已批准,工具继续执行"——重复提交被后端 404 拒绝时,用户会同时看到红绿两条自相矛盾的提示,且误以为已生效;② 审批卡两个按钮无 loading/禁用,`confirm_resolved` 回来前可连续点击发出多个请求。

**位置**:`frontend/src/stores/agent.ts:436-448`(catch 吞错);`frontend/src/views/Dashboard/AgentChat.vue:253-257`(无条件成功提示);`frontend/src/components/agent/ApprovalCard.vue:25-30`(按钮无状态)。

**影响**:错误路径反馈失真,可能诱导管理员误判操作已生效;连点产生冗余请求并叠加错误提示噪音。

**建议**:approve 返回布尔或抛出,页面仅在成功时提示;按钮点击即进入 submitting 态禁用。

### 2.12 [P2] 高危操作失败路径的留痕断链(approval_status 丢失 + 不写全站审计)

**现象**:① 工具执行器的审批状态在"通过审批后 handler 抛异常(超时/渠道冲突/未知错误)"时取不到"已过审批"的信息,落库的 `approval_status` 退为 `none`——消息表里风险等级在、审批状态却是 none,与前端已收到的 confirm_resolved(approved) 对不上;② 全部失败分支(被拒/超时/配额拒绝/执行异常)都不写 `logs` 全站审计,只有成功路径写。设计文档 4.4.5 声称"工具执行、审批变迁……全落库(双轨)",6.2 声称审计双轨。

**位置**:`backend/app/services/agent/registry.py:215-231`(异常分支 approval_status="none")、`:237-246`(审计仅在成功路径)。

**影响**:全站审计流里看不到失败的高危操作尝试(被拒的 delete_channel、超时的 sandbox_exec 等),事后追责只剩会话内单轨;设计文档验收口径 3"审批记录可在库中对齐"在失败分支断裂。

**建议**:`_run_with_gate` 内用容器记录"是否已过审批",异常分支据此落 `approved`;失败/超时/拒绝路径补写轻量 admin 日志(至少覆盖 L1/L2)。

### 2.13 [P2] agent_message.content 为 TEXT(64KB),长输出将使整个任务异常终止

**现象**:tool 结果落库前有 8KB 截断是安全的;user 消息受 schema 限制(16000 字符)贴边可过;唯独 **assistant 正文**是整轮原始输出,落库前无任何截断,只受模型 max_tokens 约束——配了大输出上限的模型单轮长输出(CJK 下)可超 TEXT 64KB,MySQL 严格模式抛 "Data too long",异常穿透主循环由任务级兜底收尾,**整个任务硬终止且该轮内容全部丢失**。同族风险:落库的 `tool_name`(String(64))来自模型生成文本,幻觉出超长工具名同样使 insert 失败。上次全面排查中 chat_record 三列正是因同一 64KB 上限改的 MEDIUMTEXT,本表属同类先例。

**位置**:`backend/app/models/agent_message.py:29`(Text)、`:33`(tool_name String(64));`backend/app/services/agent/maintain_loop.py:535-539`(assistant 无截断落库)、`:578`;对照 `docs/数据库设计文档.md` chat_record 扩容先例。

**影响**:概率低但后果是任务级崩溃;与既有先例完全同类。

**建议**:content 升 MEDIUMTEXT(存量库需手动 DDL),或落库前对 assistant 正文做字节级截断兜底;tool_name 落库前截断到 64 字符。

### 2.14 [P2] sandbox_exec 工具级超时文档漂移:30 秒 vs 实际 480 秒

**现象**:工具注册语句为 `timeout=480`,而设计文档附录 A 写"30s*"并配脚注"30s 是工具级超时";同文档 2.4 又写"拨测/巡检/搜索类自声明更长(40–480s)"——附录 A 与 2.4 自相矛盾,附录 A 是错的。

**位置**:代码 `backend/app/services/agent/tools/sandbox_tools.py:78`;文档 `docs/维护Agent设计文档.md:400、403`(附录 A)与 `:115`(2.4)。

**影响**:文档宣称的工具级护栏比实际紧 16 倍。容器内 `timeout` 包裹(默认上限 120s)仍是单条命令的真实上限,但工具级 480s 内可连续执行多条长命令;按附录 A 理解护栏会误判,而该表自称"与代码逐一核对"。

**建议**:附录 A 该行改为 `480s*`,脚注改为"工具级 480s;单条命令另有容器内 timeout 包裹(默认上限 120s,可配)"。

### 2.15 [P3] token 估算双计历史,tool_calls 参数又不计入

**现象**:估算函数声称"最近一轮官方 prompt_tokens + 其后新增字符数/4",实现却把**全部消息**的 content 字符求和加在 last_prompt_tokens 之上——历史被双计,估算比真实占用虚高(约两成到一倍),70% 压缩线提前触发,与前端水位条(官方 prompt_tokens 口径)不一致。同时估算、脱水、压缩三处都只统计 `content` 字段:assistant 的 tool_calls arguments(save_skill 草稿可达 32KB、沙箱命令 4000 字)既不计入也不被收缩,在单 user 轮的长任务里压缩也无法沿 user 边界折掉它们——大参数任务反而可能实际超窗而压缩始终不触发,最终被上游 400 打断(并与 2.5 叠加诱发误降级)。

**位置**:`backend/app/services/agent/maintain_loop.py:269-272`(估算)、`:464`(触发判断)、`:275-310`(压缩同口径)、`:251-266`(脱水仅处理 role=tool 的 content)。

**建议**:估算改为"last_prompt_tokens + 本轮新增消息字符÷4";字符统计纳入 `tool_calls[].function.arguments`;考虑对窗口外大参数做占位收缩。

### 2.16 [P3] 脱敏闭环两处盲区:管理员消息明文 + 畸形参数原样

**现象**:① `rotate_channel_key` / `create_channel` 场景管理员按设计把新密钥打在对话里,该 user 消息以**明文**持久化到 agent_message、被导出端点原样输出为 .md 文件、并在任务存续期随每轮请求发往大脑上游——tool_calls 侧有脱敏闭环,用户消息侧完全没有对应处理;② 工具参数脱敏函数在 JSON 解析失败时**原样返回**,而 finish_reason=length 截断恰恰最常产生残缺 JSON——执行虽被截断防御拒绝,落库与上行却未设防,残缺参数中若嵌有密钥片段即明文入库并可导出。

**位置**:`backend/app/services/agent/maintain_loop.py:354`(user 原文落库)、`:165-178`(解析失败原样返回)、`:529-533、558-559`(落库与 digest 用其结果);`backend/app/router/maintain_agent.py:124-145`(导出原样输出)。

**影响**:上游渠道密钥扩散到数据库、导出文件与大脑上游;导出文件尤其容易脱离原管控环境。与红线 1"库里不存密钥原文"的精神冲突(该红线目前只覆盖 tool_calls 与工具结果)。

**建议**:user 消息落库做"存储/导出用掩码版、执行上下文用原文"的双版本(与 tool_calls 同策略);参数脱敏解析失败时做子串级兜底(至少过密钥形态正则);导出端点对全文再过一遍形态掩码。

### 2.17 [P3] 审批决议与 300 秒超时的微竞态

**现象**:等待超时路径无条件把结果置为 `timeout`,决议路径也无条件覆盖。当管理员的批准恰好落在超时触发的同一事件循环轮次,可能出现:approve 端点已返回"approved"并写入审计日志,而执行器拿到的是被超时覆盖后的 "timeout" 按拒绝处理——审批结果、审计记录、实际执行三者不一致。窗口为微秒级,概率极低但真实存在。

**位置**:`backend/app/services/agent/approvals.py:63-70`(wait 超时置 timeout)与 `:72-83`(resolve 不检查既有 result 直接覆盖)。

**建议**:两侧均先判 `if pending.result is not None: return`,首个到达者胜出。

### 2.18 [P3] 任务/总线登记表永不清理,异常任务滞留内存

**现象**:`_TASKS`/`_BUS` 两个模块级字典只增不删(全文无对应 pop)。正常结束的任务仅剩小对象,但异常终止或被 stop 取消的任务,其存储的异常带 traceback,会钉住整个执行协程帧——包括完整会话历史(含 8KB 级工具结果)——直至进程回收;done Task 的异常从未被检索还会触发 "Task exception was never retrieved" 噪音。滞留的旧总线还会参与 2.2 的 task_inactive 误判。

**位置**:`backend/app/services/agent/maintain_loop.py:52-53、120、364`(无任何清理路径)。

**建议**:`_task_main` 收尾(finally 或 done callback)中清理两个字典条目。

### 2.19 [P3] 长任务中途不校验余额,可扣穿为负

**现象**:余额校验只发生在"解析目标模型"时(首轮),而模型纪元在任务内冻结(2.3)→ 实际整个任务只校验一次;后续每轮照常扣费,余额为负也继续跑。设计文档 3.2"余额不足时链路自然 402"只在下一次任务启动时成立。默认 ¥2 成本上限兜底了敞口,但上限可在设置页调大。

**位置**:`backend/app/services/agent/maintain_loop.py:431-440`(仅纪元变化时调 resolve_target);`backend/app/services/relay_service.py:120-124`(余额校验在其中)。

**建议**:每轮 settle 后检查余额,≤0 时注入提示并以 error/task_paused 收尾;或修订文档口径。

### 2.20 [P3] 参数只校验必填不校验类型,布尔传字符串反转语义

**现象**:参数校验只查 required 缺失。如 `update_channel(status="false")`——字符串 "false" 为真值 → `update["status"]=1`,**本想停用实际启用**;数值参数传字符串也被静默转换。模型不守 schema 时无护栏也无报错。

**位置**:`backend/app/services/agent/registry.py:140-146`(仅必填校验);`backend/app/services/agent/tools/channel_tools.py:155-156`(truthy 判断)。

**建议**:对 schema 声明为 boolean/integer/number 的参数做类型检查,不符即回可行动错误。

### 2.21 [P3] 内置 SOP 与 v0.14 工具集脱节,引导模型放弃现成工具

**现象**:v0.14.0 已恢复 `rotate_channel_key`(设计决策 #16 专门为修复"凭证到期只能播报不能处置")、v0.10.0 已开放 create_model/update_model(决策 #6),但两份内置 SOP 仍按旧边界表述:渠道排障 SOP 两处写"凭证失效只能引导管理员去渠道管理页手工换密钥,Agent 不经手密钥";新模型上线 SOP 写"Agent 只读模型配置,创建/改价请去模型管理页"。模型按 SOP 执行会在这些场景主动绕开现成工具,与系统提示词(v0.14.0 口径)自相矛盾。

**位置**:`backend/app/agent_skills/channel-troubleshooting.md:14、19`;`backend/app/agent_skills/model-onboarding.md:23、28`。

**建议**:同步更新两份 SOP 的处置建议(凭证失效 → `rotate_channel_key`;配置变更 → `update_model` / `create_model`)。
